# SmartBill AI

SmartBill AI is a single-shop retail billing application. The backend is the
source of truth for prices, discounts, GST, invoices, payments, and reports.
The optional AI assistant is separated from checkout and uses approved
read-only business queries.

## Project layout

```text
smartbill-AI/
  backend/
    app/
      routers/       FastAPI endpoints
      services/      Billing, invoice PDF, AI, and RAG logic
      main.py        Application and production startup checks
      database.py    SQLite engine, sessions, and schema checks
      models.py      SQLAlchemy data models
      schemas.py     Request and response validation
      database_backup.py
      database_migrations.py
    tests/           Tests use temporary SQLite databases
    requirements.txt
    venv/            Existing Python environment; keep source outside it
  frontend/
    src/             React pages and centralized API client
    .env.example
  docs/
```

The application does not manage stock. Old stock columns and inventory tables
are retained in the database model for backward compatibility only; checkout
does not check, change, or report stock.

## Technologies

- Python 3.14, FastAPI, Uvicorn, SQLAlchemy, SQLite, and ReportLab.
- React, TypeScript, and Vite.
- Optional OpenAI-compatible chat and embedding endpoints. No AI provider is
  required for billing, products, invoices, customers, or reports.

## Local setup

Use the existing `backend/venv`; do not recreate it. If dependencies are
already installed, there is no need to reinstall them. From PowerShell:

```powershell
Set-Location .\backend
.\venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Owner credentials are loaded from `backend/.env`; the password is stored as a
PBKDF2-SHA256 hash and the session signing secret is generated and persisted
automatically on first startup. Keep this ignored file private. The owner
username and password are configured once and remain unchanged across restarts.

In another PowerShell window:

```powershell
Set-Location .\frontend
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npm run dev -- --host localhost
```

Open `http://localhost:5173`. Vite proxies `/api` requests to FastAPI so the
frontend and API share one browser origin and the HTTP-only session cookie
works without frontend credentials or cross-origin cookie configuration.
`frontend/.env` contains only the public `/api` path. Never put passwords,
session secrets, or AI keys in frontend configuration.

Backend routes are available at `http://127.0.0.1:8000`; `/docs` is the
interactive API documentation, `/health` is the liveness check, and `/ready`
checks database connectivity.

### Tests and checks

Run from `backend/`:

## Configuration

| Variable | Purpose |
| --- | --- |
| `SMARTBILL_ENV` | `development` locally; `production` enables strict startup checks. |
| `SMARTBILL_OWNER_USERNAME` | The single configured owner account. |
| `SMARTBILL_OWNER_PASSWORD_HASH` | PBKDF2-SHA256 hash generated by `app.auth.hash_password`. |
| `SMARTBILL_SESSION_SECRET` | Random signing key; use at least 32 characters and keep it private. |
| `SMARTBILL_COOKIE_SECURE` | Set to `true` for HTTPS. Production startup requires it. |
| `SMARTBILL_CORS_ORIGINS` | Comma-separated exact frontend origins, without trailing slashes. |
| `SMARTBILL_TRUSTED_HOSTS` | Production API hostnames, separated by commas. |
| `SMARTBILL_DATABASE_PATH` | SQLite file path; defaults to `backend/smartbill.db`. |
| `SMARTBILL_RAG_DB_PATH` | Separate RAG SQLite file path; defaults to `backend/assistant_rag.sqlite` locally. |
| `SMARTBILL_TIMEZONE` | Shop timezone; defaults to `Asia/Kolkata`. |
| `SMARTBILL_AI_BASE_URL` | Optional HTTPS OpenAI-compatible API base URL in production. |
| `SMARTBILL_AI_API_KEY` | Optional provider key; backend environment only. |
| `SMARTBILL_AI_CHAT_MODEL` | Optional chat model name. |
| `SMARTBILL_AI_EMBEDDING_MODEL` | Optional embedding model name for document search. |
| `SMARTBILL_AI_TIMEOUT_SECONDS` | Provider timeout, from 1 to 120 seconds; defaults to 25. |
| `VITE_API_BASE_URL` | Public frontend API base URL; defaults to `/api` for the Vite proxy. |

Local backend settings are loaded from `backend/.env`. Do not commit secret
files. `.gitignore` excludes local environment files, virtual environments,
databases, and build output. For production, provide secrets through the
hosting platform's secret manager and use the explicit HTTPS CORS and trusted
host configuration described below.

## Database safety, backup, and recovery

SQLite is appropriate for a small, single-shop installation with modest traffic
and one backend process. It allows only one writer at a time. Keep the database
on a local or provider-managed persistent disk—not a shared network filesystem.
This workspace is currently under OneDrive: OneDrive synchronization is **not**
a database backup or a safe live-database replication strategy. The default
database location remains unchanged; move it only through a planned, verified
backup-and-restore process.

The application creates a new database when no database file exists. It checks
the schema of an existing database without changing it. Production startup
never creates or migrates schema. If an existing database needs changes, it
fails with an instruction to take a backup and run an explicitly approved
migration.

Create a consistent online snapshot using SQLite's
[Online Backup API](https://www.sqlite.org/backup.html) (not a plain file copy
while the application is running):

```powershell
Set-Location .\backend
.\venv\Scripts\python.exe -m app.database_backup backup `
  --source .\smartbill.db `
  --destination D:\SmartBillBackups\smartbill-2026-11-25.sqlite
.\venv\Scripts\python.exe -m app.database_backup backup `
  --source .\assistant_rag.sqlite `
  --destination D:\SmartBillBackups\assistant-rag-2026-11-25.sqlite
```

Use a new destination name for each backup. The command validates the snapshot
with `PRAGMA quick_check`. Backups contain customer, invoice, and document data;
restrict access, encrypt them at rest, and keep an encrypted copy in a separate
location. Schedule daily backups using Windows Task Scheduler or the hosting
provider's backup service and periodically test a restore. The CLI does not
schedule, encrypt, or upload backups.

To recover, stop the backend first. Verify the backup, then restore it. Replacing
an existing database requires explicit confirmation; the command first makes a
timestamped safety backup of the current file:

```powershell
.\venv\Scripts\python.exe -m app.database_backup restore `
  --backup D:\SmartBillBackups\smartbill-2026-11-25.sqlite `
  --target .\smartbill.db `
  --confirm-overwrite
```

The same procedure applies separately to the RAG database. Restart the backend
and check `/ready`, then confirm that recent invoices and documents are
available.

### Schema updates

Schema changes are currently additive SQL updates, not a versioned Alembic
migration history. No migration was applied to the shop database during this
audit. If a reviewed code update requires an existing database migration:

1. Stop the application and create a verified backup.
2. Confirm the restore procedure on a temporary copy.
3. Obtain approval before applying the migration to the shop database.
4. Run the explicit command below with a new backup destination:

```powershell
.\venv\Scripts\python.exe -m app.database_migrations --apply `
  --backup D:\SmartBillBackups\pre-migration-2026-11-25.sqlite
```

This command creates a backup first and then applies the existing additive
schema updates. If it fails, do not repeatedly rerun it; preserve the backup
and investigate the schema mismatch.

Move from SQLite to PostgreSQL when multiple registers or backend instances
need concurrent writes, the database must be shared across hosts, write
contention becomes visible, or managed database failover and point-in-time
recovery are required. That move needs a separately tested data migration and
approval; it is not performed here.

## Optional AI and document search

AI is off until configured. No local model is bundled or downloaded. Configure
the provider only after reviewing its current prices, rate limits, privacy,
retention, and data-processing terms:

```powershell
$env:SMARTBILL_AI_BASE_URL = "https://provider.example/v1"
$env:SMARTBILL_AI_CHAT_MODEL = "provider-chat-model"
$env:SMARTBILL_AI_EMBEDDING_MODEL = "provider-embedding-model"
$secureKey = Read-Host "Provider API key (if required)" -AsSecureString
$env:SMARTBILL_AI_API_KEY = [System.Net.NetworkCredential]::new("", $secureKey).Password
```

The key stays in the backend. Questions, document text during embedding, and
retrieved document passages may be sent to that provider. Product, customer,
invoice, and sales figures are retrieved through approved backend functions;
the model cannot run SQL or change business records. Provider redirects are
disabled and production provider URLs must use HTTPS. If AI fails, ordinary
billing and shop management continue to work.

RAG documents are stored separately from invoice data. The service accepts
UTF-8 `.txt`, `.md`, and `.csv` documents, limits each document to 1 MB, and
caps the local store at 200 documents and 20,000 chunks. RAG remains a basic
cosine-similarity search over local JSON vectors; retrieval quality should be
checked with the shop's real documents before relying on it for policy
decisions. Use the separate RAG backup command above.

There is no application-level AI token or cost dashboard. The generic provider
adapter cannot infer a provider's billing rules; monitor usage and spend in the
provider's own dashboard. Exact AI costs cannot be estimated until a provider,
model, and usage level are selected. Keep AI disabled if cost monitoring or the
provider's data terms are not acceptable.

## Production and deployment

Do not expose the development server (`--reload`) to the internet. This
application is designed for **one backend process and one SQLite database**:
session revocation and rate-limit counters are in memory, so multiple workers
or replicas would not share those states.

Passwords are stored as PBKDF2-SHA256 hashes. The owner session cookie is
HTTP-only, signed, and expires after eight hours; logout revokes it in the
running process. State-changing requests require a CSRF token. Production
requires HTTPS, explicit CORS origins, and trusted host names. These controls
do not replace operating-system updates, firewall rules, encrypted backups,
provider security, or monitoring. There is one owner account and no MFA or
per-user permissions.

For production, provide all of these backend variables through the hosting
platform's secret/configuration manager:

```text
SMARTBILL_ENV=production
SMARTBILL_DATABASE_PATH=/persistent/smartbill/smartbill.db
SMARTBILL_RAG_DB_PATH=/persistent/smartbill/assistant_rag.sqlite
SMARTBILL_OWNER_USERNAME=owner
SMARTBILL_OWNER_PASSWORD_HASH=<generated PBKDF2-SHA256 hash>
SMARTBILL_SESSION_SECRET=<random secret of at least 32 characters>
SMARTBILL_COOKIE_SECURE=true
SMARTBILL_CORS_ORIGINS=https://shop.example.com
SMARTBILL_TRUSTED_HOSTS=api.example.com
SMARTBILL_TIMEZONE=Asia/Kolkata
```

The persistent directories must already exist, and the billing database file
must already contain a complete schema. Production startup checks the file and
schema read-only; it will refuse to create or alter them. Keep the billing and
RAG databases on separate persistent paths.

Build the frontend with its public HTTPS API URL set at build time:

```powershell
Set-Location .\frontend
$env:VITE_API_BASE_URL = "https://api.example.com"
npm ci
npm run build
```

Publish `frontend/dist/` to a static host. Run the backend behind a TLS
terminating reverse proxy with one worker and no reload:

```sh
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 \
  --workers 1 --proxy-headers --forwarded-allow-ips "$TRUSTED_PROXY_IP"
```

Set `TRUSTED_PROXY_IP` to the actual trusted proxy address or documented
provider range; never trust forwarded headers from arbitrary clients. Configure
HTTPS at the proxy, exact HTTPS CORS origin(s), trusted API hostname, persistent
storage, and automatic encrypted backups. Frontend and API should use the same
site (for example `shop.example.com` and `api.example.com`) because the owner
cookie uses `SameSite=Strict`.

### Steps before publishing

1. Choose a provider and region, and approve expected monthly charges.
2. Make and verify separate billing-database and RAG-database backups.
3. Decide on persistent storage and restore the data to it while the app is
   stopped. Do not point production at the OneDrive-synced working copy.
4. Check schema readiness. If migration is needed, review the data impact,
   test on a copy, and obtain approval before applying it.
5. Configure the production secrets, HTTPS domains, trusted proxy, CORS, and
   persistent paths listed above.
6. Build and publish the frontend; start one backend worker without `--reload`.
7. Verify `/health`, `/ready`, sign-in/logout, CSRF-protected writes, product
   management, a test invoice/PDF, customer history, reports, and AI-disabled
   behavior. Use a test database first.
8. Schedule encrypted off-site backups and test recovery before processing
   real sales.

## Troubleshooting

- **Owner sign-in is unavailable:** for local use, check that `backend/.env`
  contains the configured username and PBKDF2-SHA256 password hash; the session
  secret is generated automatically. Production secrets must be configured
  through the hosting platform's secret manager. Plain owner passwords are not
  accepted.
- **Database schema is incomplete:** startup does not migrate an existing
  database. Create a verified backup, review the migration, and get approval
  before running `app.database_migrations`.
- **Browser reports a CORS or sign-in problem:** use the exact frontend origin
  in `SMARTBILL_CORS_ORIGINS`, use HTTPS in production, and keep frontend/API
  on the same site for `SameSite=Strict` cookies.
- **Database is locked:** check for a second backend process. Keep SQLite on a
  local persistent disk, use one worker, and use the backup utility rather
  than copying a live database file.
- **Assistant shows unavailable:** check optional provider URL, model names,
  key, timeout, provider limits, and HTTPS. Billing does not depend on AI.
- **Reports use the wrong business day:** set `SMARTBILL_TIMEZONE` to a valid
  IANA timezone available on the host. Windows has no bundled IANA timezone
  database; `Asia/Kolkata` has a fixed-offset fallback, while other Windows
  timezones may require operating-system timezone data.

## Known limitations

- One configured owner account; no multi-user roles, MFA, or account recovery.
- Sessions and rate limits are process-local; use one backend process.
- SQLite schema updates are not yet tracked by a versioned migration framework.
- No automatic backup scheduler, external log/alert service, or application AI
  cost dashboard is configured.
- RAG is local SQLite/cosine search with bounded storage, not a dedicated vector
  database. Validate answers against source documents.
- Profit is unavailable because historical invoice lines do not preserve
  purchase-price snapshots.
- Legacy inventory columns/tables remain for compatibility, but are unused by
  the application.
